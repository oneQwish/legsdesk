# Как устроено рабочее место юриста

## 1. Общая схема

```
  ИСТОЧНИКИ                         РАБОЧЕЕ МЕСТО                        ПОТРЕБИТЕЛИ
  ─────────                         ─────────────                        ───────────
  1С (OData / HTTP-сервис) ─┐
  Excel / CSV отчёты ───────┤                                        ┌──▶ 1С (HTTP-сервис / файл)
  sot.db конвейера OCR ─────┼─▶ коннекторы ─▶ API ─▶ база ─▶ API ─▶──┼──▶ будущая собственная система
  папки со сканами/PDF ─────┤   (in)                PostgreSQL  (out) └──▶ отчёты (CSV/XLSX)
  другие системы ───────────┘                          │
                                                       ▼
                                        юристы в браузере (вход по AD)
```

- **Коннектор** — программа `connectors/lawdesk_connect.py` + файл настроек `.toml`. Он читает источник и
  отправляет данные в рабочее место через API (направление `in`) или забирает изменения и записывает их
  наружу (направление `out`). Подробно — [коннекторы](коннекторы.md).
- **API** — единственная дверь в данные. Им пользуются и интерфейс, и коннекторы, и 1С (если писать обмен
  кодом). Прямо в базу ничего не пишется.
- **База** — PostgreSQL. Хранит дела, значения по источникам, документы (карточки), сроки, журнал.
- **Файлы документов** — в хранилище: сейчас папка на сервере, позже — система документооборота
  (переключается настройкой `LAWDESK_STORAGE_BACKEND`).

Рабочее место **не привязано к 1С**. 1С — один из источников и один из потребителей, наравне с остальными.
Имена источников («1С», «отчёт», «OCR» …) — просто текст в настройках коннектора.

## 2. Главная идея: значения по источникам и конфликты

Каждый источник сообщает **своё** значение поля дела — это «наблюдение». Рабочее место не перезаписывает
одно значение другим, а хранит все рядом и сравнивает:

| Ситуация | Статус поля | Что видит юрист |
|---|---|---|
| Два и более источника дали одно значение | подтверждено | значение, зелёная метка |
| Значение есть только у одного источника | один источник | значение, серая метка |
| Источники расходятся | **конфликт** | поле в очереди конфликтов: варианты с источниками и цитатами |
| Расходятся суммы, а у дела есть признаки обжалования | возможна апелляция | то же + подсказка «сверьте с актом апелляции» |
| Юрист выбрал значение | решено юристом | выбранное значение, кто и когда решил, комментарий |

Сравнение «умное»: `141 611,96 руб.` = `141611.96`; `15.03.2027` = `2027-03-15`; «Пономарёва Е.В.» =
«пономарева е.в.»; списки истцов — без учёта порядка.

Решение юриста попадает в **журнал** и в **ленту изменений**, откуда коннектор `out` или 1С забирает его
по курсору. Если после решения какой-то источник пришлёт **новое** значение — конфликт откроется снова
(старые, уже рассмотренные значения конфликт не открывают).

## 3. Дело и его номера

Дело ищется так:
1. по **УИД**;
2. если УИД нет — по **коду суда + номеру** (основному или любому из старых номеров, М-материалу…).

Если пришёл новый УИД, а номер уже занят делом с другим УИД, создаётся **отдельное** дело с
предупреждением: номер дела не уникален (бывает один номер у разных дел). Дубли сливает юрист в
карточке дела («Слить дубль»): номера, значения, документы и сроки переходят в одно дело.

## 4. Процессуальные сроки

Считаются автоматически из актов дела по ГПК РФ:

| Акт | Срок | Статья |
|---|---|---|
| Решение (от даты мотивированного решения) | апелляционная жалоба — 1 месяц | ст. 321 |
| | вступление в силу — на следующий день после срока обжалования | ст. 209 |
| Заочное решение (если известна дата вручения) | заявление об отмене — 7 рабочих дней | ст. 237 |
| Апелляционное определение | кассационная жалоба — 3 месяца | ст. 376.1 |
| Любое другое определение | частная жалоба — 15 рабочих дней | ст. 332 |

Перенос с нерабочего дня — по ст. 108 ГПК, по **производственному календарю**, который загружает
коннектор. Если календарь года не загружен, используются выходные + праздники по ст. 112 ТК без
переносов, а срок помечается «*». Юрист может поправить дату — тогда автоматический пересчёт её больше
не трогает.

## 5. Данные (таблицы базы)

| Таблица | Что хранит |
|---|---|
| `cases` | дела: УИД, суд, номер, юрлицо, объект, истцы, ответственный… |
| `case_aliases` | все номера дела |
| `case_values` | поля дела: итоговое значение и статус |
| `value_observations` | значения по источникам (с ключом записи, документом, страницей, цитатой) |
| `documents` | карточки документов (файл — в хранилище) |
| `deadlines` | процессуальные сроки |
| `calendar_days` | производственный календарь |
| `events` | журнал и лента изменений |
| `services`, `api_keys` | подключённые сервисы и их ключи (хранится только хэш ключа) |
| `users` | пользователи (роль — из групп AD при каждом входе) |
| `saved_views` | подборки фильтров пользователей |
| `tasks` | очередь задач для сервисов |

Схема создаётся автоматически при старте сервера.

## 6. Безопасность

- Люди входят доменной учёткой; роль (администратор / юрист / просмотр) — по группе AD.
- Сервисы входят API-ключом с ограниченными правами; ключ можно отозвать в любой момент.
- Все действия пишутся в журнал, включая просмотр файлов документов.
- В базе есть персональные данные — сервер должен быть только во внутренней сети, с HTTPS.
- Пароли внешних систем в файлах настроек **не хранятся** — только в переменных окружения
  (`password_env`, `api_key_env`) или в файле `секреты.bat`, который не попадает в git.
